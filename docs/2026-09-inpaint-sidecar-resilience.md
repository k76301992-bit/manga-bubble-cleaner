# إصلاح انهيار مسار الترميم المدرب في الإنتاج (2026-09)

## الأعراض من سجلات النشر (2026-09-01 → 2026-09-04)

- كل طلبات الترميم عبر Big-LaMa فشلت بنسبة **100%**: `trained inpainting FAILED: The operation was aborted due to timeout` ثم `fetch failed`.
- النتيجة في كل مهمة: `inpaintWithTrainedModel done: 0/N regions repaired` — كان التبييض يعمل بالحشو المسطح الاحتياطي فقط.
- بعد أول دقيقتين من التشغيل لم ينجح أي ترميم مدرب حتى نهاية عمر الحاوية (3 أيام).

## الأسباب الجذرية

1. **لا يوجد إشراف على خدمة Python:** `scripts/start-standalone.sh` كان يشغّل `python3 app.py &` مرة واحدة؛ عند أول انهيار تبقى الخدمة ميتة إلى الأبد (سياسة إعادة تشغيل Railway تعيد تشغيل الحاوية عند موت العملية الرئيسية Node فقط).
2. **ازدحام خيوط على وحدة CPU مقيدة:** لم يكن `app.py` يحدد `torch.set_num_threads` ولا `cv2.setNumThreads`؛ الحاوية تعلن أنوية المضيف كثيرة بينما حصة cgroup جزء من نواة واحدة، فيتنافس عشرات الخيوط حتى يفشل اقتصاص 90×50 في الانتهاء خلال 20 ثانية، ثم يُقتل العملية بالذاكرة بعد تكدس الطلبات المتوازية.
3. **مهلة افتراضية ضيقة بلا إعادة محاولة:** `INFERENCE_TIMEOUT_MS=20000` (وثّقها `.env.railway.example` أيضاً) تُجهض طلبات سليمة، ولا يوجد Retry لتغطية فجوة إعادة تشغيل الخدمة.
4. **مهلة Qwen ضيقة للصفحة الكاملة:** سجل الإنتاج يُظهر صفحة سليمة استغرقت 161 ثانية وأخرى أُجهضت عند سقف 180 ثانية، فيخسر الطلب كله وينزل إلى كاشف التباين.

## الإصلاح

| الملف | التغيير |
|---|---|
| `server/inference-service/app.py` | ضبط خيوط torch/OpenCV/OpenMP قبل الاستيراد (`INFERENCE_NUM_THREADS`، افتراضي `1`) + **تسخين** النموذج عند الإقلاع (ترميم وكشف مصغّران) حتى لا يدفع أول طلب حقيقي كلفة التهيئة. |
| `server/standalone/inpainting-client.ts` | المهلة الافتراضية `120s` بدل `20s` + إعادة محاولة (`INFERENCE_RETRIES`، افتراضي `2`) بتراجع تدريجي + **طابور تزامن عام** (`INFERENCE_MAX_CONCURRENCY`، افتراضي `2`) يمنع تراكض المهام المتوازية على الخدمة. |
| `scripts/start-standalone.sh` | حلقة إشراف تعيد تشغيل خدمة Python تلقائياً بعد `INFERENCE_RESTART_DELAY_SEC` (افتراضي `3`) ثوانٍ من أي انهيار، مع تمرير TERM/INT لأطفاء نظيف. |
| `server/standalone/cleaner.ts` | مهلة Qwen للصفحة الكاملة افتراضي `300s` وقابلة للضبط عبر `QWEN_REQUEST_TIMEOUT_MS` دون إعادة بناء. |
| `.env.railway.example` / `DEPLOYMENT-ENV.md` | تحديث القيم الافتراضية المثبتة وتوثيق المتغيرات الجديدة. |

## سلوك ما بعد الإصلاح

- انهيار خدمة Python → إعادة تشغيل خلال ~3 ثوانٍ (تحميل النموذج ~0.5 ثانية)، وإعادة المحاولة في Node تغطي الفجوة.
- طلب واحد كبير متأخر لا يُجهض قبل 120 ثانية، والمهام المتوازية تنتظر في طابور مرتب بدل قتل الخدمة.
- أول طلب حقيقي بعد الإقلاع سريع بفضل التسخين.

## كيفية التحقق بعد النشر

- راقب السجل: يجب أن ترى `warm-up inpaint finished` عند الإقلاع و`inpaint OK ... attempt=1` مع `regions repaired` أكبر من صفر.
- أي سطر `[standalone-api] inference sidecar exited (code=...) — restarting` يعني أن الحلقة الجديدة تعمل بدل موت دائم.
